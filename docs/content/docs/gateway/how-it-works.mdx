The Gateway is an OpenAI-compatible generation layer between your application and model providers. It accepts a request, selects the requested model, and streams the provider response back through a reliability pipeline.

## Request lifecycle

<Mermaid
  chart={`

    participant Renderer as OpenUI renderer

    App->>Gateway: Responses or Chat Completions request
    Gateway->>Provider: Normalized model request
    Provider-->>Gateway: Streaming model output
    Note over Gateway: Validate and correct OpenUI Lang
    Gateway-->>App: Compatible response stream
    App-->>Renderer: Relay stream
    Note over Renderer: Render approved application components

1. Your backend sends a Responses or Chat Completions request using a `{provider}/{model}` identifier.
2. The Gateway authenticates the request and routes it to the selected provider.
3. The provider begins streaming model output.
4. For OpenUI generation, the Gateway parses and validates the OpenUI Lang stream as it arrives.
5. When the stream contains a correctable language or schema error, the Gateway repairs it before forwarding the affected output.
6. Your backend relays the compatible stream to the browser, where the renderer maps it to your components.

## Reliability boundaries

The Gateway corrects OpenUI Lang. It does not replace application validation, tool authorization, or UI error boundaries. Your application still owns component behavior, user permissions, tool execution, and the final rendering environment.

Provider fallback is a separate reliability layer. It handles provider or model availability failures; [error correction](/docs/gateway/reliability/error-correction) handles invalid OpenUI Lang already produced by a model.

## Conversation state

Responses supports three history patterns:

| Pattern                           | Where history lives                                       |
| --------------------------------- | --------------------------------------------------------- |
| Full `input` history              | Your application stores and resends prior turns.          |
| `previous_response_id`            | The Gateway chains stored responses.                      |
| `conversation` with `store: true` | The Gateway stores a named thread and its response items. |

Chat Completions remains message-based: your application owns the `messages` array and resends the relevant history on each turn. See the [Conversations API](/docs/gateway/api/conversations) for persistent Responses threads.

## Observability is independent

The Gateway prevents or recovers from failures in the generation path. Observability records errors and context from the application runtime. It can be connected whether generation uses the Gateway or calls a provider directly. See [Observability Overview](/docs/observability).
